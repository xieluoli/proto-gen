# 原型评审清单

> **适用范围**：设备无关。原型生成或大改后套用，一次性出问题清单再统一修，不逐条发现逐条改。
> 执行者：`agents/prototype-reviewer.md`（只读 subagent）。本文档是它的规则单一源。
>
> 本清单只管**通用**规则。项目自有的主题 token 值、外壳结构、版本命名等特化规则，写在项目自己的 `.claude/agents/prototype-reviewer.md` 里，不要回写本文件。

## P1 · 组件复用（最高优先级）

原型的价值在于沉淀可复用的组件，不在于每张图各写一套样式。

- 任一 UI 元素 MUST 先在 [`css-components.md`](css-components.md) 索引表里找已有类名；找到就直接用，**不得**自造同义类名（`.card-box` / `.panel-wrap` 这类）。
- 索引表里没有的，MUST 先判断是否可由已有类名 + 组合实现（如 `.btn.btn-ghost.btn-sm`），组合不出来才允许新增。
- 新增的类名 MUST 记录在问题清单的「新增组件」段，注明：类名 / 用途 / 为什么已有组件覆盖不了。
- 页面自有 `<style>` 里 MUST 只放本页特有布局，不得复制通用组件样式（那些归 `shared.css`，由注入脚本回填）。
- **同族按钮的长相不复制第二份**：新按钮与既有按钮长相相同、只是位置或方向不同时，把新类名挂进既有规则的**选择器组**共用同一个声明块（`.wizard-skip, .wizard-back, .wizard-cancel { … }`），自己只给定位。不要复制一份声明再改两行。
- **类名要对得上动作**：一颗做「取消安装」的按钮不能挂 `.wizard-skip`——研发读到会当成同一个动作。长相可以共用，语义必须各有各的类名。
- **母版候选**：同一 CSS 块或 HTML 片段在同目录原型中重复 **3 次及以上**，标注为母版候选，建议抽进 `shared.css`。本轮只标注，不动手拆。

## P2 · 基于最新原型迭代

新原型 MUST 站在最近一次产出上继续，不得从旧版本或空白起步。

- **动态定位基准**：用 Glob 收集目标文件同级 / 兄弟目录下的既有原型，按目录名或修改时间取**最新一份**作基准。**不要**在规则里写死某个版本号——写死的那天起它就开始过期。
- 目标需求未特殊说明的**通用区域**（外壳窗口、侧边栏、顶部工具栏、卡片、按钮、间距）MUST 与基准视觉一致。比对方法：`grep` 同名类名在基准文件中的定义，与目标文件逐项对齐。
- 基准里已修正过的问题（如某个对齐、某个状态色），MUST 不在新原型里复发。
- 若目标原型有意偏离基准，MUST 在问题清单里说明偏离点与理由，由人确认，而不是静默不同。
- **新增状态切片与基准屏逐像素同构**：只改状态本身的差异，位置与尺寸不动——否则人对比两屏时看到的是无关抖动。
  > 换标签（`<button>` → `<div>`）会改变文字度量：`<button>` 行高取 UA 的 `normal`，`<div>` 继承页面行高，同样内容能差出几 px。换完必须显式补回 `line-height`，并用 `getBoundingClientRect()` 实测复核，**不能只看截图像**。

## P3 · 结构契约与注入

- 三段结构合规：`toc-sidebar` 全文件唯一；每个 `.proto-with-prd` 内**恰好一个**外壳 + **恰好一个** `.prd-panel`；不允许一图多 PRD 或一 PRD 跨多图。
- 每个 section 在 `toc-sidebar` 有对应入口，锚点可跳。
- `<head>` 三对 `@proto-gen` 标记块（theme / shared / highlight）存在且**已由脚本回填**，无空块；标记块之间无手写内容。
- 页面可直接双击打开，无本地 css / js 依赖。
- **可交互原型的数据只留 DOM 一份来源**：换卡 / 换选项时从被点的 DOM 节点上取值，不另维护一份 JS 数组。
- **多张切片复用同一段脚本时按 section 作用域绑定**：`document.querySelector` 单选会全部撞到第一张切片上。全局监听（`document` 上的 click / keydown）注册一次即可，不要写在 `forEach` 里随切片数量翻倍。
- **跨切片共享同一业务对象的，要么全部同步，要么在注释里点名哪几屏刻意不跟**：几张切片的 PRD 都写着「与某屏逐字相同」，漏一处一交互就当场露馅。
- 只作 JS 钩子、无 CSS 定义的类名，加一句注释，免得研发去找样式。

## P4 · PRD 面板

- 面板标题「功能概览」。
- 每条按 [`prd-rules.md`](prd-rules.md) 的模板写：加粗元素名前缀 + 「展示…」描述；按视觉布局**从上到下**排列；一个可感知元素一条，单一职责。
- **写产品，不写实现**：类名、颜色、px、组件出处（「沿用 vX.X」）、变更历史（「原来那条已撤销」）一律不进面板。面板写的是这一屏展示什么、控件在各状态下变成什么、点了会怎样。详见 [`prd-rules.md`](prd-rules.md) 的「面板写产品，不写实现」。
- **面板与实现要对得上**：改了实现就回扫面板。最常见的缺陷不是写错，是「改了实现没回扫描述」——旧步数、旧类名、旧按钮文案、已经被新切片拍板却还留着的待决项。
- **已被拍板的待决要删掉**：某条待决已由新增切片或人的决策解决了，面板里的那条要删，否则与新切片的描述直接矛盾。
- 改动型原型只描述本次改动，不复述未变部分。
- 不写交互批注体（那些属于 spec.md，不进 PRD 面板）。

## 脚手架不入生产

`data-comp` / `data-target` 属性与 `prd-highlight.js` 是评审脚手架。发现即标注「交付研发前需剥离」，**不计作原型缺陷**。剥离清单见 [`prd-highlight.md`](prd-highlight.md)。

## 输出格式

只读审查，不改文件。按下列分段输出，每条给 `file:line` + 问题 + 建议改法；无问题的段写「通过」：

1. **P1 组件复用**（含「新增组件」与「母版候选」两个子项）
2. **P2 与基准原型一致性**（先写清用了哪份作基准、怎么定位到的）
3. **P3 结构契约与注入**
4. **P4 PRD 面板**
5. **脚手架待剥离**
6. **风格沉淀建议** —— 见下

末尾一句总评：**可交付** / **需修订**（列出必改项）。

### 风格沉淀建议段怎么写

审查过程中会浮现「这次新立的做法值得固化」的东西。把它们收在这一段，供人确认后写进项目设计文档或 `shared.css`：

- **本轮新增/改动的组件模式**：类名 + 用途 + 是否建议进 `shared.css`
- **重复出现但尚未固化的写法**：出现在哪几个文件、建议抽成什么
- **与基准的有意偏离**：偏离点 + 理由 + 是否应反向更新基准规范
- **已过期的规范条目**：项目规范文档里写死、但与当前原型现状矛盾的条款（如写死的版本号、已被替换的组件名）

这一段**只出建议，不落笔改任何文档**。是否采纳、写到哪，由人决定。
